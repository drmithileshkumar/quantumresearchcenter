What makes a quantum programming result independently reproducible?

Reading guide · preparation and approach

Starting point: Earlier programming chapters; relevant constructions from Quantum Computing and Quantum Algorithms.

Anchor example: Package a complete algorithm implementation with tests, execution records, and analysis.

This lesson includes explanations, worked examples, and problems with solutions. Advanced results whose proofs are outside the chapter are identified explicitly.

16.1 Project Structure

A project is reproducible when another reader can reconstruct its task, circuit, assumptions, and evidence. A plot without the program and execution record is not enough.

16.1.1 Modules, notebooks, and tests

Keep circuit factories, experiment drivers, and tests separate. A notebook can explain an experiment, while a script runs it from a fresh process. Tests should include a small independently solvable case, asymmetric ordering checks, and phase-sensitive inputs. Never make importing a module submit a hardware job.

16.1.2 Dependencies and version control

Pin tested dependencies and record the Python version. Keep credentials out of version control. Record source changes so that a result points to the code that produced it. A requirements file captures direct dependencies; a full environment lock and platform note improve exact reproduction. Updating a package requires rerunning relevant examples rather than assuming unchanged behavior.

Problem 16.1. Why does the target bit vary in the capstone output?

Worked solution

It remains in minus, which gives a fair computational-basis result. The useful secret is in the other bits, so the decoder excludes the target bit.

16.2 Experiment Records

16.2.1 Saved circuits and configurations

Save a circuit artifact as well as its drawing. QPY preserves Qiskit circuit structure for supported version compatibility, and the companion checks an in-memory save/load round trip. Keep the logical circuit, compiled circuit, layout, parameter values, and seeds when compilation is involved. A diagram alone may omit global phases or parameter metadata.

16.2.2 Results, metadata, and execution costs

An experiment record should identify the problem, input size, access assumptions, success criterion, shots, qubits, logical and compiled counts, execution type, package versions, and measured outputs. Exact local simulation, noisy simulation, and hardware must be labeled distinctly. Confidence intervals and error budgets belong beside conclusions, not hidden in raw logs.

Problem 16.2. What changes if the secret is all zeros?

Worked solution

The oracle has no CNOTs and the input Hadamards cancel, so the output secret is all zeros. This is an important edge case.

16.3 Capstone Project

16.3.1 Specification and implementation

The capstone implements Bernstein–Vazirani for an arbitrary supplied binary secret. It prepares a minus target, uses one CNOT for each one bit in the oracle description, applies Hadamards, and reads the input register. The known secret lets us verify construction; it is not being discovered by a program that lacks access to its own source. The algorithmic query model treats the constructed oracle as the supplied interface.

16.3.2 Evaluation, limitations, and documentation

The companion uses secret 1011, checks circuit serialization, samples, and verifies every input-register result. The target is measured too and appears at the left of Qiskit’s full string; bits[1:] extracts the input register. Extend the project across lengths, test zero and all-one secrets, report oracle gate growth, and compare with the classical query baseline under the same oracle contract. The result is a reproducible implementation study, not a hardware speedup claim.

The complete companion below can be downloaded as chapter_16.py. Run it from a terminal using the course environment. Assertions check the stated behavior; printed counts are samples, not universal expected output.

"""Runnable companion for Quantum Programming, Chapter 16."""
import io, json, sys
from importlib.metadata import version
from qiskit import QuantumCircuit, qpy
from qiskit.primitives import StatevectorSampler
from qiskit.quantum_info import Operator

secret = "1011"  # Written high bit first.
n = len(secret)
qc = QuantumCircuit(n+1)
qc.x(n); qc.h(range(n+1))
for qubit, bit in enumerate(reversed(secret)):
    if bit == "1":
        qc.cx(qubit, n)
qc.h(range(n))
# Save/load the coherent circuit before appending measurements.
buffer = io.BytesIO()
qpy.dump(qc, buffer); buffer.seek(0)
restored = qpy.load(buffer)[0]
assert Operator(qc).equiv(Operator(restored))
qc.measure_all()
counts = StatevectorSampler(seed=41).run([qc], shots=1024).result()[0].data.meas.get_counts()
assert all(bits[1:] == secret for bits in counts)
record = {"problem": "Bernstein-Vazirani", "secret": secret,
    "python": sys.version.split()[0], "qiskit": version("qiskit"),
    "seed": 41, "shots": 1024, "qubits": qc.num_qubits,
    "gate_counts": dict(qc.count_ops()), "counts": counts,
    "execution": "local ideal StatevectorSampler", "oracle_queries_per_shot": 1}
print(json.dumps(record, indent=2))

Problem 16.3. What evidence would be needed for a runtime advantage claim?

Worked solution

A scalable task and access model, matched classical baseline, complete preparation and oracle costs, execution and readout costs, comparable success and precision, and measurements or justified resource analysis over growing sizes.
