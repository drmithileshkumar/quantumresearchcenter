Until now, every measurement came at the end of a circuit. Its result went back to the host program, which could only print it or analyse it. Some devices can do more: measure a qubit partway through, and let the result decide which gates come next, while the other qubits are still in use.

How can a measurement change the remaining computation? We first meet the two operations involved, mid-circuit measurement and reset. Using a result inside the circuit runs into the old problem that a host-language if cannot see a result that does not yet exist, so we need a condition recorded in the circuit itself. Teleportation then gives a program with four measurement branches, each needing its own correction, and we must check that every branch is right, not just the average. Finally, a simulator that accepts such a circuit does not show that a device can run it, so we look at the constraints that real controllers impose.

Teleportation is a demanding test, because a single wrong correction would break exactly one branch.

12.1 Mid-Circuit Operations

A circuit with a measurement in the middle keeps running after the measurement. What becomes of the measured qubit and its result, and how can later gates use that result? We look at the measurement and the reset first, then at conditions that read a measured bit.

12.1.1 Measurement and reset

What does a measurement in the middle of a circuit do? It writes a classical bit, and it leaves the measured qubit in the basis state it reported. The other qubits stay available for later gates. A reset then puts a qubit back in \(\ket0\), so that it can be reused. If that qubit was entangled with others, the reset destroys the correlation, as we saw when we found that a reset has no inverse. Both are physical operations on a device. Neither is a Python assignment.

Which simulator can run such circuits? StatevectorSampler is meant for circuits measured only at the end. For circuits whose later gates depend on mid-circuit results, the companion uses Aer’s AerSimulator. It follows each shot down the branch selected by that shot’s measurement results.

12.1.2 Classical conditions and feedback

Suppose we want a qubit to end in \(\ket0\) whatever it held: measure it, and apply X if the result was 1. Could we write that with an ordinary Python if bit == 1: qc.x(0)? No. That line runs at construction time, when the circuit has not been executed and no bit exists. The condition has to be part of the circuit, so that the controller evaluates it during the run.

Qiskit writes such a condition as a block:

with qc.if_test((qc.clbits[0], 1)):
    qc.x(0)

Python’s with statement opens a context, and the indented lines run inside it. Here the context is if_test, and it changes what appending means. The gates appended inside the block are not applied unconditionally. They are recorded into the circuit as the body of a condition. The tuple (qc.clbits[0], 1) names the condition: classical bit 0 equals 1. Using a measurement result to choose later operations is called feedback, or feedforward. The condition must name the exact classical bit that the measurement map writes to.

12.2 Conditional Programs

With feedback we can program protocols that branch on measurement results. Teleportation is the standard example: Alice sends a qubit’s state to Bob using a shared Bell pair and two classical bits. Which correction belongs to which bit, and how can a program show that all four branches work? We derive the corrections first, then verify each branch.

12.2.1 Teleportation

The companion places the input \(\ket\psi=\alpha\ket0+\beta\ket1\) on q0. A Bell pair \((\ket{00}+\ket{11})/\sqrt2\) is made on q1 and q2 with H on q1 and a CNOT from q1 to q2. Alice holds q1, and Bob holds q2. Alice then applies a CNOT from q0 to q1 and H on q0, and measures q0 into c0 and q1 into c1. Call those results \(m\) and \(n\). The figure uses the same names.

What state does Bob hold in each branch? Writing the qubits in the order q0, q1, q2, the CNOT gives \[\tfrac1{\sqrt2}\bigl[\alpha\ket0(\ket{00}+\ket{11})+\beta\ket1(\ket{10}+\ket{01})\bigr].\] H on q0 replaces \(\ket0\) by \((\ket0+\ket1)/\sqrt2\) and \(\ket1\) by \((\ket0-\ket1)/\sqrt2\). Collecting the terms by the values \(m,n\) of q0 and q1, Bob’s qubit is left in

\[m n=00:\ \alpha\ket0+\beta\ket1,\quad 01:\ \alpha\ket1+\beta\ket0,\quad 10:\ \alpha\ket0-\beta\ket1,\quad 11:\ \alpha\ket1-\beta\ket0,\]

each with probability \(1/4\). These are \(X^nZ^m\ket\psi\). So Bob applies X when \(n=1\) and then Z when \(m=1\). This gives \(Z^mX^n\,X^nZ^m\ket\psi=\ket\psi\) exactly in every branch.

In the program, the two corrections are two if_test blocks, on qc.clbits[1] for X and on qc.clbits[0] for Z. Exchanging the two records would apply the wrong correction in branches 01 and 10.

Problem 12.1. Why apply Z controlled by c0 rather than c1?

Worked solution

The H measurement on the original input determines the phase correction. The Bell-half measurement determines the bit-flip correction. Swapping these records fails on general input states.

12.2.2 Verifying every branch

How can a program check that Bob holds \(\ket\psi\)? We cannot read amplitudes from a measurement. But if \(\ket\psi\) was made by a known preparation \(V\ket0\), then applying \(V^\dagger\) to Bob’s qubit returns it to \(\ket0\) exactly when the state is right. A measurement then gives 0 with certainty.

The companion prepares \(\ket\psi\) with \(R_y(0.7)\) and then \(R_z(0.4)\), so the state has unequal amplitudes and a nontrivial relative phase. After the corrections it applies \(R_z(-0.4)\) and then \(R_y(-0.7)\) to Bob’s qubit, and measures it into c2. Every shot, in every branch, should give c2 = 0.

Why insist on the phase? A missing Z correction changes only the sign of \(\beta\). On a basis state such as \(\ket0\) that change is invisible, and on any state with real amplitudes it is a different but plausible state. A test state with a relative phase exposes it. One test state still does not determine the whole process. Stronger validation repeats the test with other preparations, or with an input entangled with a reference qubit.

Problem 12.2. Does Bob receive the state before Alice communicates her outcomes?

Worked solution

Without the records his state is averaged over the four Pauli branches. The corrections require those classical bits, so the protocol does not signal instantly.

12.3 Execution Constraints

Our teleportation program runs on a simulator. A device has to do something harder: measure, send the bit to a classical controller, decide, and apply a gate, all while the other qubits wait. What does that require of a device, and what does it change about how we judge correctness? We take capabilities first, then timing and branch-by-branch checking.

12.3.1 Simulator and backend capabilities

If Aer accepts our if_test blocks, will a device accept them too? Not necessarily. A simulator implements the abstract circuit, while a device’s controller supports only certain conditions, certain resets and certain timing. Before submitting, we check what the chosen backend supports. A controller may evaluate only simple classical expressions, so a high-level condition may have to be rewritten. The companion runs locally and says nothing about hardware availability.

12.3.2 Latency, branches, and correctness

What does feedback cost? It can save qubits or depth. A measured and reset qubit can be reused, for example, instead of allocating a new one. But each measurement and each classical decision takes time, called latency, and the waiting qubits are exposed to noise during it.

How do we read the companion’s counts? Each key lists the classical bits as c2 c1 c0, with c0 on the right, as in our bit-order convention. So key[0] is c2, the verification bit. With seed 23 the run gave about 250 counts in each of the four branches c1 c0 = 00, 01, 10, 11, because Alice’s outcomes are random. Every key began with 0.

The final assertion requires key[0] == "0" for every key that appeared, using all, which is true only if the test holds for every item. It is a check on every observed branch. A check on the overall fraction of zeros could pass even if one rare branch were always wrong. The circuit is first passed through transpile(qc, sim), which rewrites it in the simulator’s supported instructions. Aer then returns counts through result().get_counts(), an older result interface than the primitives use.

"""Runnable companion for Quantum Programming, Chapter 12."""
from qiskit_aer import AerSimulator
from qiskit import QuantumCircuit, transpile

# q0=input, q1=Alice's half, q2=Bob's half; c0,c1 are correction records.
qc = QuantumCircuit(3, 3)
qc.ry(0.7, 0); qc.rz(0.4, 0)
qc.h(1); qc.cx(1, 2)
qc.cx(0, 1); qc.h(0)
qc.measure(0, 0); qc.measure(1, 1)
with qc.if_test((qc.clbits[1], 1)):
    qc.x(2)
with qc.if_test((qc.clbits[0], 1)):
    qc.z(2)
# Inverse of the known test preparation verifies the recovered state.
qc.rz(-0.4, 2); qc.ry(-0.7, 2)
qc.measure(2, 2)
sim = AerSimulator(seed_simulator=23, max_parallel_threads=1)
counts = sim.run(transpile(qc, sim), shots=1024).result().get_counts()
assert all(key[0] == "0" for key in counts)
print("c2 c1 c0:", counts)

Problem 12.3. Why test a nontrivial phase as well as real amplitudes?

Worked solution

A missing Z correction may be invisible on a basis state. A phase-sensitive input exposes that error.

A program whose logic is correct can still give wrong counts on a device, because the device is noisy. When a result disagrees with our prediction, how can we tell a noisy experiment from an incorrect program?
