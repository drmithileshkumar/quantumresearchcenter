Every program so far came with checks, and they were not equally strong. Counts showed only which outcomes occurred. A full matrix caught every sign. A comparison of amplitudes on a superposition found errors that a histogram could not see. We chose each check for its example, without asking in general what a check must contain.

What evidence establishes that a quantum program implements its specification? We start from a bug that passes every test on basis inputs, and it forces tests on superpositions. Comparing on superpositions raises the question of which phase differences count, and the answer depends on whether the component will be controlled. A component also makes promises about wire order and workspace, and checks of inverses and composition test some of these promises but not others. Finally, every comparison needs a tolerance, and sampled comparisons need statistics.

The aim is a set of tests in which each one rules out a specific kind of error.

9.1 Functional Tests

Suppose a component should do nothing to its qubit, and by mistake it applies Z. Which test catches the mistake? The obvious tests do not, and seeing why tells us what a functional test must compare. We find the failing test first, then decide which differences between two operations should count as errors.

9.1.1 Basis inputs and superpositions

The first attempt runs both circuits on the basis inputs \(\ket0\) and \(\ket1\) and compares the output probabilities. Both tests pass. Since \(Z\ket0=\ket0\) and \(Z\ket1=-\ket1\), the outputs differ only by a sign, and a sign changes no probability.

What input would expose the difference? One in which the sign becomes a relative phase between two amplitudes. On \(\ket+\), the identity gives \(\ket+\), while \(Z\) gives \(\ket-\). These two states are orthogonal, the most different two states can be. A Z-basis histogram still cannot tell them apart, but a comparison of amplitudes can, and so can a measurement in the X basis.

The companion makes this argument executable. Statevector.from_label("0") builds a basis state from its label, and "+" builds \(\ket+\). The method evolve applies a circuit to a state. A loop over the tuple ("0", "1") shows that the basis probabilities agree. The final checks use not to assert that the two outputs on \(\ket+\), and the two operators, are not equivalent. So a coherent contract needs tests on superpositions, comparing amplitudes, not only labels.

9.1.2 Equivalence and global phase

If we compare amplitudes, should every difference count as a bug? Take a circuit whose only content is a global phase of 0.3, set through phase.global_phase = 0.3. On its own, it makes the same predictions as the identity, so a test that rejects it would be wrong. Operator.equiv accepts two operators that differ by one overall phase factor, and the companion asserts that the identity and this circuit pass.

Two kinds of difference are not covered by that freedom. A separate phase on each basis column is not global: \(Z=\operatorname{diag}(1,-1)\) differs from \(I\) by a phase on one column only, and the equivalence check rejects it. And under control, even a global phase becomes a relative phase on the control, as we derived for controlled operations. So the companion also checks that the controlled identity and the controlled phase circuit are not equivalent.

The rule for a test, then, is to allow a global phase only for a component that will never be controlled, and to record that assumption.

Problem 9.1. Why does testing Z on zero miss the bug?

Worked solution

Zero is an eigenstate of Z with eigenvalue one. Test plus to expose the relative sign between zero and one.

9.2 State and Workspace Checks

Functional tests check the action on the useful registers. A component promises more than that: its wires are attached in a stated order, its workspace starts and ends clean, and it can be inverted and combined with others. Which tests check these promises, and which only seem to? We take wire order and workspace first, then inverses and composition.

9.2.1 Register ordering and ancilla cleanup

Which input exposes two wires attached in the wrong order? Not a symmetric one: the Bell pair and the all-zero input look the same either way round. An asymmetric input, such as X on qubit 0 alone, makes the two orders give different outputs.

For workspace, we have three checks of increasing strength. The weakest measures the ancilla and requires outcome 0 with probability 1. A stronger one computes the reduced state of the useful registers and compares it with the predicted pure state. The strongest, possible when the system is small, compares the whole joint state with the predicted useful state times \(\ket0\) on the ancilla. A clean workspace must factor away from the useful registers in this way.

Suppose a contract promises that the ancilla starts in \(\ket0\). Then we test only inputs with the ancilla in \(\ket0\). Such tests say nothing about other ancilla states. That is acceptable, because the contract never promised anything about them.

9.2.2 Inverse and composition tests

Is “\(U\) followed by its inverse gives the identity” a good test of \(U\)? Recall that inverse() computes the inverse from \(U\)’s own gates. So the product is the identity whatever \(U\) does, right or wrong. The test checks the inverse construction, not the specification, and we pair it with a test against an independent prediction.

Composition tests have a different value. Joining two components can reveal a wire contract that one of them breaks, or a phase convention that one of them omitted. Feeding in a randomly chosen superposition is another useful check, because it exercises all the amplitudes and phases at once. For a small component, though, the complete matrix remains the decisive test. A random input gives evidence about one input. The matrix covers all of them.

Problem 9.2. Can two individually global-equivalent gates always be substituted under control?

Worked solution

No. Their differing phase acts only in the control-one branch and becomes observable relative to the control-zero branch.

9.3 Statistical Tests

Every comparison so far used a tolerance, and every sampled one used a statistical window. A tolerance that is too loose accepts bugs, and one that is too tight rejects correct programs. How do we choose these numbers rather than guess them? We treat rounding and approximation first, then sampling.

9.3.1 Numerical tolerances

How large are rounding errors in an exact calculation? A computer stores numbers with about 16 significant digits, so each operation can introduce an error near \(10^{-16}\). A small gate sequence accumulates a few of these. An absolute tolerance such as \(10^{-12}\) therefore leaves a wide margin above rounding while remaining far below any real mistake.

A circuit that is approximate by design is different. Its error is part of the method, so the tolerance must come from an analytic bound on that error. We will meet such a bound when we approximate a time evolution by a product of simpler steps.

Why not use a relative tolerance alone, accepting \(a\) when \(|a-b|\le r|b|\)? When the expected value \(b\) is 0, the condition becomes \(|a|\le0\). An amplitude that should vanish but comes out as \(10^{-17}\) then fails. So near zero we need an absolute tolerance, and a test should state which tolerance it uses. It should also state which notion of equality it uses, exact or up to global phase, and which distance it measures, entry by entry or over the whole matrix.

9.3.2 Sampling uncertainty and regression tests

A sampled test can fail even when the program is correct. For the coin we chose a window of 6.4 standard deviations, which a correct program leaves with probability about \(2\times10^{-10}\). A suite of many such tests multiplies that chance, so windows must be set with the whole suite in mind. Demanding exact counts, as we saw, rejects most correct runs.

Fixed seeds help in another way. With a seed, a sampled test gives the same result on every run, so a change signals a change in the code or environment. But a seed can also hide a test that passes only for that seed. So sampled tests sit beside deterministic checks of states and operators, which have no randomness at all.

Finally, how do we know a test can fail? We give it a wrong program. The companion includes the Z bug deliberately and asserts that the coherent test rejects it.

"""Runnable companion for Quantum Programming, Chapter 9."""
import numpy as np
from qiskit import QuantumCircuit
from qiskit.quantum_info import Operator, Statevector

identity = QuantumCircuit(1)
wrong = QuantumCircuit(1)
wrong.z(0)
# Basis output probabilities match, but relative phase differs.
for label in ("0", "1"):
    state = Statevector.from_label(label)
    assert np.allclose(state.evolve(identity).probabilities(), state.evolve(wrong).probabilities())
assert not Statevector.from_label("+").evolve(identity).equiv(Statevector.from_label("+").evolve(wrong))
assert not Operator(identity).equiv(Operator(wrong))
phase = QuantumCircuit(1)
phase.global_phase = 0.3
assert Operator(identity).equiv(Operator(phase))
assert not Operator(identity.to_gate().control()).equiv(Operator(phase.to_gate().control()))
print("Relative-phase bug detected; controlled global phase also checked")

Problem 9.3. Is a larger tolerance always safer?

Worked solution

It reduces false failures but can accept real bugs. Choose it from the numerical and approximation budgets, and include known incorrect examples that should fail.
