Quantum Hardware Execution

How do we run a tested program on hardware and interpret the result?

Chapter direction

Starting point: Earlier programming chapters; relevant constructions from Quantum Computing and Quantum Algorithms.

Anchor example: Execute a small validated circuit and compare hardware measurements with local predictions.

This lesson includes explanations, worked examples, and problems with solutions. Advanced results whose proofs are outside the chapter are identified explicitly.

  1. 11.1 Execution Setup
  2. 11.2 Runtime Workloads
  3. 11.3 Result Analysis

11.1 Execution Setup

The same Bell circuit can be tested locally and submitted remotely. The two executions need different claims: a local simulation predicts an ideal model, while a hardware result reports a particular device at a particular time.

11.1.1 Backend selection and credentials

Choose an accessible backend that supports the circuit’s width, instructions, and control requirements. Account setup and credentials belong outside source files. The companion uses a synthetic local backend by default. It does not access an account or submit a job unless the user explicitly supplies --submit and an exact --backend name.

11.1.2 Executable circuits and mapped observables

Compile against the selected backend’s target before submission. For an Estimator workload, map each logical observable through the compiled circuit’s layout, for example with observable.apply_layout(compiled.layout). Otherwise the observable may refer to the wrong physical wires. The example uses a Sampler, whose measurement mapping is carried by the compiled circuit.

Problem 11.1. Does importing the Runtime package submit a circuit?

Worked solution

No. A run call on a remote execution object is the submission action. Keep that action separated from module import and local testing.

11.2 Runtime Workloads

11.2.1 Submitting and retrieving jobs

A Runtime Sampler is constructed with the selected backend as its mode. Calling run submits the workload and returns a job handle. Save the job identifier immediately so a later process can recover the record. The submit branch below uses configured account access; it has not been run on hardware for this course edition.

11.2.2 Execution modes and budgets

Job, session, and batch modes organize execution differently. Their availability and accounting depend on the service and account. Estimate circuits, shots, and expected device usage before submission; do not infer a fixed free quota. A short Python statement can launch substantial work. Keep the explicit submission boundary visible in reusable teaching code.

Problem 11.2. Why map an Estimator observable after layout?

Worked solution

The logical qubits may have moved. Measuring Z on a different physical qubit can answer a different question even when the compiled state is correct.

11.3 Result Analysis

11.3.1 Metadata and provenance

Save the backend name, execution time, package versions, compiled circuit, layout, shots, options, and returned metadata. A count table without those facts cannot be reliably compared with another run. Device calibration drifts, so a later result may differ even with the same source circuit. Report what was actually executed rather than an intended logical circuit alone.

11.3.2 Simulation, hardware, and uncertainty

The local path compiles against GenericBackendV2 and prints its resource counts. The remote path constructs an ISA circuit, submits 1024 shots, prints the job ID, and retrieves counts. Only the local path is included in automated checks. No hardware outcomes are invented; the example’s Bell-state ideal prediction remains 00 and 11 with equal probability, while a device may also produce errors.

The complete companion below can be downloaded as chapter_11.py. Run it from a terminal using the course environment. Assertions check the stated behavior; printed counts are samples, not universal expected output.

"""Runnable companion for Quantum Programming, Chapter 11."""
import argparse
from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit.providers.fake_provider import GenericBackendV2
from qiskit_ibm_runtime import QiskitRuntimeService, SamplerV2

def build(backend):
    circuit = QuantumCircuit(2)
    circuit.h(0); circuit.cx(0, 1); circuit.measure_all()
    return generate_preset_pass_manager(backend=backend, optimization_level=1,
                                        seed_transpiler=17).run(circuit)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--submit", action="store_true", help="Explicitly submit a paid/allocated hardware job")
    parser.add_argument("--backend", help="Exact accessible hardware backend name")
    args = parser.parse_args()
    if not args.submit:
        compiled = build(GenericBackendV2(2, seed=3))
        print("Local compilation only; no account accessed and no job submitted.")
        print(compiled.count_ops())
    else:
        if not args.backend:
            parser.error("--backend is required with --submit")
        service = QiskitRuntimeService()  # Uses a separately configured account.
        backend = service.backend(args.backend)
        compiled = build(backend)
        job = SamplerV2(mode=backend).run([compiled], shots=1024)
        print("Submitted job:", job.job_id())
        print(job.result()[0].data.meas.get_counts())

Problem 11.3. What is missing from a claim that hardware “gave 95% success”?

Worked solution

The task, success definition, shots and uncertainty, device and time, circuit and layout, execution options, and comparison baseline are all needed.

Hardware can sometimes act on measurement results before a circuit finishes. We next program that feedback explicitly.
